# 私人文章增补提案

这是知识入库主线的第一段：把已整理候选变成已有文章的精确增补方案，供本人查看、生成新版本和导出。合并与 Worker 实际更新是不同步骤；功能不具备 GitHub 写权限、批准 API 或发布任务。

## 使用与范围

1. 在候选「审阅整理」核对正文、来源、Domain 和已有目标文章，保存为「已整理」。
2. 打开「入库提案」，明确点击准备；每次生成最多调用一次模型，共用每日调用/token 预算。已有版本的打开、切换、导出和结果核对不调用模型。
3. 查看文体、依据、编辑问题、完整差异和完整修改后文件。模型整理后的新文字仍需本人技术/行文核对及公开范围确认。
4. JSON 导出是私人 v1 提案，不是批准。它兼容 Python schema、摘要与语义门禁；真实提案的整仓校验与构建后续接入，当前 UI 如实标为未运行。

首段只允许给已注册文章追加 Markdown。服务端取完整原文和路径，不允许模型重写旧文字、选择文件路径或改元数据。新文章、Topic 注册、关系/视图调整及纠错替换需要后续结构编辑能力，不伪装成普通增补。重复或证据不足的结果留私有，不创建空提案。

模型接收绑定当前构建的五份完整架构/操作/行文规范、目标文章全文、有限相关检索结果及本人核对的依据，按八类叙事整理。本人核对记录不表示模型访问了外部网页，结构检查不表示事实或文风已通过审阅。

## 数据与边界

- 复用现有提案、不可变版本、候选关联和请求表，无需 migration。提案为 `draft`；不写 `approvals` 或发布 `jobs`。
- `POST /api/candidates/:id/proposals` 只接收 `request_id`、`candidate_version`、`snapshot_revision`。服务端核对当前 main/部署/索引、规范摘要、本人核对与目标归属。
- 相同请求 ID 核对输入摘要并返回既有结果。超时或中断先查结果，不自动再次计费；进行中的会话租约阻止并发编辑和旧结果提交。
- `GET /api/candidates/:id/proposals` 返回最新版本；带 `request_id` 只读核对请求结果。`GET /api/proposals/:id?version=N` 返回不可变版本、完整 before/after 及审阅状态，`/export?version=N` 私有导出 JSON。
- 所有 API 沿用 Owner JWT、同源边界与写标记；响应 `private, no-store`。提案不送公共 reader iframe、GitHub 或 CI artifact。历史版本可查看，不代表仍可发布。
- `publication.review_note` 把文体、候选版本和编辑说明一起绑定到提案摘要。`publication` 只是未来拟公开范围，不是已获得授权。
- 沿用现有删除范围：删除会话会删除消息和候选，独立的不可变提案与审计记录保留；缺失候选依据的提案标为过期，不可据此发布。删除确认中明确说明保留范围。

## 自动化与上线

现有 PR CI 使用真实 Worker/本地 D1 和合成 HTTP fixture，验证完整规范、完整差异、Python schema/摘要/语义构建兼容、不可变版本、权限、预算、幂等、截断/丢失响应和基线变化。DOM 回归覆盖预览、导出、重新打开和焦点恢复。不调用付费模型或真实 D1，不替代每份真实提案发布前的整仓校验。

先部署 Pages 新版快照，再通过受保护的 `Update private Atlas Worker` 更新运行时。旧快照缺少规范时停止准备并提示同步；原有学习问答、候选和文章阅读保持可用。
